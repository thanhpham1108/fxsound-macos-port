Verified results and remaining limits are tracked in [`IMPLEMENTATION_STATUS.md`](IMPLEMENTATION_STATUS.md). The audit below records the source findings and original staged plan.

The installed `FxSound.exe` reports 1.2.16.0; the audited [`FxSound.jucer`](https://github.com/fxsound2/fxsound-app/blob/4383180e02ff435d191f71220e8da41f9fa06951/fxsound/FxSound.jucer) reports 1.2.15.0. Therefore the checkout is not established as the exact shipped source. REA's static PE import record is in [`evidence/fxsound-pe-imports.json`](../evidence/fxsound-pe-imports.json), Evidence `ev_22561e50d7c8d3aae77adb813bd3a7dfab7a8851b68c229e3ae119c72ef246da`, executable SHA-256 `bcf18555832bde067b2bc9e2b5a893c1d887b6680494cdafa785517d22184286`. Static source answers the core signal-path question, so no live disassembly was attempted.

## Verified source path

1. Windows policy COM sets the virtual output as default: `audiopassthru/src/sndDevices/sndDevicesSet.cpp::SetDefaultEndpoint` (line 112). WASAPI loopback on that endpoint is set in `sndDevicesSetupDevices.cpp` (line 170); physical playback is initialized around line 474.
2. `audiopassthru/src/AudioPassthru/AudioPassthruPrivate.cpp` captures at lines 495/513, sets format at 532, calls `DfxDsp::processAudio` in place at 551, then plays to the physical device at 570. The buffer is float32 despite the legacy `short*` API cast (comment at 548).
3. `dsp/DfxDspPrivate.cpp::processAudio` (181) enters `dfxpUniversalModifySamples` (185); `dsp/ptutil/dfxp/dfxpUniversal.cpp` chunks large buffers (157) and passes float32 to `dfxpModifyRealtypeSamples` (178).
4. `dsp/ptutil/dfxp/dfxpProcessReal.cpp` handles bypass (125) and graphic EQ first (141/152). `dsp/ptutil/DspUtil/GraphicEq/GraphicEqProcess.cpp` calls `sosProcessBuffer`; the original filter coefficients and stereo state update live in `dsp/ptutil/Filt/FiltCalcBiqd.cpp::filtCalcParametric` and `dsp/ptutil/SOS/SosProcess.cpp::sosProcessBuffer` (528). Master gain, balance, normalization and leveling are in that SOS stage.
5. Optional binaural processing runs at ≤48 kHz around `dfxpProcessReal.cpp:172`. The main chain calls `comProcessWaveBuffer` at 366. `dsp/ptechDsp/Play/Play32/Play32.c` applies Aural/Fidelity (643), Lex/Ambience (665), Wide/Surround (681), Bass (693), optional crossfeed, then Maximizer (872). Its comment at 867 states Maximizer remains active when Dynamic Boost is off.
6. The worker renders processed frames through `sndDevicesDoPlayback.cpp` (105–118). `sndDevicesDoCapture.cpp` (172–214) handles silent and discontinuous WASAPI packets.

Power-off in FxSound is not always transparent: `dfxpProcessReal.cpp:160–165` runs `GraphicEqProcess_MasterGainOnly` when EQ is enabled. A flat EQ can still run volume leveling. The initial prototype's `--bypass` is an explicitly **dry**, state-preserving pass-through; it is not represented as FxSound's power-off mode.

## Reuse decisions and stages

The existing interface is JUCE (`fxsound/FxSound.jucer`), so retain its components and preset controls. Replace Windows platform calls around audio endpoints, registry, tray placement, hotkeys and crash reporting. The current project exports only Visual Studio; create a macOS JUCE/CMake target after the audio backend is proven. Preserve the original DSP equations and stage order. The first native slice in `native/` ports **only** FxSound's parametric SOS coefficient and stereo sample equations. It omits graphic EQ band mapping, normalization, leveling, Aural, Lex, Wide, Bass, Maximizer and binaural processing. It is an architecture and file-processing prototype, not a sound-parity claim.

Next implementation gates:

1. Build `native/fx_dsp` and `fxwav` on Apple Silicon; run the same WAV at 44.1/48 kHz through dry bypass, unity EQ, a known EQ setting and gain. Compare against FxSound's Windows golden harness with identical PCM/settings and report peak and per-sample error. The upstream `web/dsp-tutorial/tests/golden/` harness is Windows/VS2022 specific and writes `HKCU\SOFTWARE\DFX`, so save/restore that key before use.
2. Add a macOS Core Audio process tap using a selected physical output UID, excluding our own Core Audio process object. Use `CATapMuted`, a private aggregate and one IOProc clock for capture, DSP and output. Require stereo float32 at first; reject format mismatches. Stop on output-device/rate changes, then rebuild off the audio thread. Do not silently resample or route to a second output clock. A limited implementation is now in `macos/FxTap.mm`, with CLI device selection and stop-on-change listeners. A 48→44.1 kHz speaker rate switch caused the prototype to stop; the test restored 48 kHz. Automatic restart and a device UI remain open.
3. Port the full original DSP, presets (`dsp/DfxDspPreset.cpp` VALS/qnt mappings), and JUCE controls. Keep registry and file I/O off the audio callback; use a parameter snapshot delivered between buffers. Add device selection, fallback handling, and a visible bypass control on the same output route.
4. Package/sign/notarize a macOS 14.2+ arm64 app, include AGPL notices and corresponding source, run live device/permission/dropout/latency tests. An ad hoc signed arm64 prototype app now builds and runs; release signing, notarization, full device testing, complete system-wide support and parity remain **unverified**.

The full Maximizer is a priority for stage 3: a loud 1 kHz input at 0.8 amplitude with +6 dB EQ produced thousands of float output samples above full scale in the current slice. This is an observed clipping risk, not a claim about the original FxSound's output.

## Capture API decision

[Apple's Core Audio tap sample](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps) requires macOS 14.2+, `NSAudioCaptureUsageDescription`, and prompts for System Audio Recording permission when reading the aggregate. `CATapDescription` supports process exclusion and `muteBehavior`; [`CATapMuted`](https://developer.apple.com/documentation/coreaudio/catapmutebehavior) suppresses the original audible path while the tap exists. `CATapMutedWhenTapped` still yielded audible overlap in this prototype's first live test, so the code uses the stronger mode. Resolve the app PID to a Core Audio process `AudioObjectID` with [`kAudioHardwarePropertyTranslatePIDToProcessObject`](https://developer.apple.com/documentation/coreaudio/kaudiohardwarepropertytranslatepidtoprocessobject) before exclusion. Exclude any future output helper too. This avoids recording our own rendered output and a feedback loop. A private aggregate is a temporary Core Audio object; it requires no separately installed virtual driver. The initial device-scoped tap will cover apps playing to that device, not arbitrary outputs elsewhere.

ScreenCaptureKit audio is available from macOS 13, but its documented capture route does not mute source playback, making replacement audio harder. An [Audio Server Driver plug-in](https://developer.apple.com/documentation/coreaudio/creating-an-audio-server-driver-plug-in) could become an explicit virtual default output but needs privileged installation and more lifecycle work. The Core Audio tap is the first route to validate.

## Licenses and dependencies

FxSound source and this derivative slice are AGPL-3.0-or-later (FxSound copyright notices remain in `upstream/fxsound` and attribution above). Distribution must include the applicable license and corresponding source for the derivative. FxSound's README lists JUCE, but its generated `AppConfig.h` has GPL/Indie/Pro text; pin the actual JUCE version and license before bundling it. Preset translations come from a separate `Resources` submodule and need their own license inventory. Do not bundle Gilroy/Noto font assets until their rights and notices are verified. REA is an investigation tool and is not a runtime dependency. The native prototype uses only the C++ standard library.
